# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An MCP (Model Context Protocol) server that exposes WLAN Pi capabilities - device info, service management, Wi-Fi scanning, packet capture, profiler, Bluetooth, VLANs - to AI assistants. It is a thin bridge to the `wlanpi-core` API on `https://localhost:31415`: every tool and resource goes through that API, and nothing runs local subprocesses or reads local files. Keep it that way - if a capability has no wlanpi-core endpoint, the endpoint gets added upstream first.

Almost all of that API is REST. The one exception is **packet capture**, which wlanpi-core exposes only as a WebSocket (`/api/v1/streaming/capture`) - so `wlanpi_mcp/capture/` speaks that protocol instead of HTTP. That is still core-API-only: same host, same JWT, still no local subprocess. The one deliberate exception to "no local file" is the file-backed capture family (`tools/capture_file.py`, see below), which persists the pcapng bytes it receives over that same WebSocket to a managed directory and reads them back - a scoped relaxation, not licence to read arbitrary device files or add other non-core transports.

## Commands

```bash
# Setup (Python >= 3.13)
pip install -e ".[testing]"

# Run all tests / one file / one test
pytest
pytest tests/test_auth.py
pytest tests/test_auth.py::test_passes_token_to_downstream_context

# Run the server locally
python -m wlanpi_mcp --transport stdio   # default; direct MCP client invocation
python -m wlanpi_mcp --transport streamable-http   # HTTP daemon mode (uvicorn, stateless, /mcp), how systemd runs it

# Build the Debian package (dh-virtualenv, installs to /opt/wlanpi-mcp)
dpkg-buildpackage -us -uc
```

`asyncio_mode = auto` is set in pyproject.toml, so async tests don't need `@pytest.mark.asyncio`. Lint and format tooling is configured via tox: `tox -e lint` (`ruff check` then `mypy`), `tox -e formatcheck` (`ruff format --check`), and `tox -e format` (`ruff format`).

## Architecture

- `wlanpi_mcp/server.py` - `create_server()` builds the `MCPServer` (mcp 2.x; was `FastMCP` in 1.x, pinned `>=2.3.0,<3`) instance and wires every module in. `create_http_app(mcp)` builds the streamable HTTP ASGI app and is the one place the daemon's transport settings (`/mcp` path, stateless, JSON responses, DNS rebinding protection off) live, because 2.x takes them on `streamable_http_app()` rather than the constructor; `__main__` and `tests/test_server.py` both use it. All tool/resource/prompt modules follow the same pattern: a top-level `register(mcp, client)` function containing `@mcp.tool()` / `@mcp.resource()` decorated closures. Adding a capability = new module in `tools/` or `resources/` + a `register()` call in `server.py`. The "Phase 1/2/3" comments reflect the order features were built, nothing more.
- `wlanpi_mcp/client/core_client.py` - `CoreClient`, the single async httpx client for wlanpi-core. Module-level singleton via `init_client()`/`get_client()`, created in `__main__.py` and passed to `register()` functions.
- `wlanpi_mcp/elicit.py` - asking the user directly with MCP elicitation, the multi-round-trip (MRTR) way. The daemon is stateless, so `ctx.elicit()` has no back channel: a tool returns an `InputRequiredResult` (`elicit.ask()`), the client asks the user and retries the same `tools/call` with `inputResponses` plus our `requestState`, and `elicit.answer()` reads the reply. It only engages on a 2026-07-28 request whose `_meta` clientCapabilities declare the mode (`can_form`/`can_url`); everything else gets the tool's old behaviour, so every caller keeps a "cannot ask" path. `requestState` is sealed by the SDK's `RequestStateBoundary` under `elicit.request_state_security()`: a per-process AES key (a round pending across a restart fails with -32602 and the client starts over), bound to the tool name, its arguments and **the caller's JWT** (the SDK default binds to its own OAuth identity, which this server does not use). An answer counts only for a key the sealed state says we asked, so a client cannot pre-fill a confirm. `confirm()` returns None to go ahead, else the result to return (`not_performed` on decline, which is a result, not an error). Tools that confirm take a `ctx: Context` parameter and are listed in `hints.CONFIRMED`, which `tests/test_tool_annotations.py` pins as a subset of the destructive set: the Pi owns tool-specific confirms, so a client or extension should not add its own.
- `wlanpi_mcp/tasks.py` - the MCP Tasks extension (`io.modelcontextprotocol/tasks`, SEP-2663), hand-built on the SDK's `Extension` API because mcp 2.3.0 has no runtime for it (python-sdk #2806 / PR #3005; swap to the SDK's `Tasks()` when it ships). `Tasks(TASK_TOOLS)` intercepts an allowlisted `tools/call` (`server.TASK_TOOLS`) and, only when that request declared the extension on 2026-07-28, answers `resultType: "task"` and runs the call as a background asyncio job; otherwise the call runs synchronously as before. `tasks/get` returns the tool's exact `CallToolResult` once `completed` (a tool error is `completed` with `isError`, never `failed`), `tasks/cancel` cancels the job so the tool's own `finally` cleanup runs, and `tasks/update` answers in-task `request_input()`. Each task is bound to `sha256(JWT)`; another token's task id answers -32602 like an unknown one. State is in memory only (a restart forgets tasks; their captures stop with their sockets). Tools report progress with `tasks.set_status()`/`tasks.reporting()`, both no-ops outside a task; `start_pcap_file` under a task waits for its capture to end (a cancel stops it gracefully and keeps the file), and `profile_clients` exists only as a task.
- `wlanpi_mcp/config.py` - pydantic-settings `Settings`, loaded from environment or `/etc/wlanpi-mcp/config.env`. The service allowlist is not here: `list_allowed_services` reads it from core (`GET /api/v1/system/services`) and core enforces it on every `/service/*` call, so there is no local copy to drift. `ALLOW_POWER_CONTROL` (default true) gates `reboot_device`/`shutdown_device`.
- `wlanpi_mcp/capture/` - the capture WebSocket client, used by `tools/capture.py`. `ws_client.py` derives the ws/wss URL from `WLANPI_CORE_URL` and drives the protocol (`CaptureSocket`: auth first, then `configure`/`start`/`subscribe`/`list_sessions`/`stop`; `CaptureError` carries core's error code so callers can branch on `INTERFACE_IN_USE`). `pcapng.py` and `dot11.py` are a stdlib-only incremental pcapng reader and radiotap/802.11 dissector **vendored from wlanpi-core `tools/capture_harness/capture_harness.py`** - keep them in sync with that reference rather than growing a parallel dissector, and do not pull in scapy/dpkt. The dissector has since been extended past the harness on purpose (the pcapng reader also yields a per-frame timestamp; `dot11.py` adds full radiotap decode, all frame type/subtype names, per-frame source/dest addresses, decoded management results, full RSN/WPA AKM/cipher/PMF detail, and the QBSS/BSS Load element) - these extensions are ours, so re-sync the *shared* parsing logic without dropping them. The streaming capture tools (`capture_scan`/`capture_observe`) return dissected summaries rather than raw pcap inline, but they now also tee the raw pcapng bytes to a file in the managed capture directory (via `CaptureSocket.consume`'s optional `raw_sink`) and return its `pcap_path`/`pcap_bytes`, so a summary can be verified against the frames with `fetch_pcap_file`; teeing is best-effort (`storage.try_open_capture_file`) so a storage problem never breaks a capture. Two views come out of the same frames - an AP table (`ScanTable.to_result()`, one row per BSSID with the compact security label plus full `akm`/`pairwise_ciphers`/`group_cipher`/`pmf`, and `stations`/`channel_utilization` from the QBSS Load element when present) and a per-frame log (`FrameLog`, exact per-kind counts always, plus up to `max_frames` records carrying addresses, radiotap and any decoded result). The per-frame record list is bounded by `max_frames` (0 = counts only, no records) so a busy capture can stay a summary rather than a text pcap — but the bound is caller-controlled, not a hard ceiling: a negative `max_frames` returns every frame, and there is no longer a `MAX_FRAMES_CAP`. For a genuinely complete capture prefer the file-capture tools over an unbounded `capture_scan`.

Capture ownership matters: a capture lives with its WebSocket, so closing the socket stops it. Owner flows must `stop()` and close in a `finally` - never leave an ownerless capture on the device - and every capture result states its `role` (`owner`/`subscriber`), `session_id` and running `config`. `capture_scan` auto-subscribes when the interface is already owned by another session. `CHANNEL_SET_FAILED` events are non-fatal and are surfaced in `channel_issues`: on single-radio devices, hops fail while the managed `wlan0` scans, and a partial capture must not be reported as complete.

File-backed capture (`wlanpi_mcp/tools/capture_file.py`: `start_pcap_file`/`stop_pcap_file`/`list_pcap_files`/`fetch_pcap_file`) is the one place that deliberately relaxes two of the invariants above - it returns *raw pcapng*, not a dissected summary, and it writes then reads a local file - to allow captures longer than the 60 s streaming window. `start_pcap_file` starts a capture, hands the owning `CaptureSocket` to a background asyncio task (`CaptureSocket.consume_raw`, which writes the pcapng byte stream verbatim instead of dissecting), and returns immediately with the on-device path and `session_id` while the capture keeps running past the tool call. That task still `stop()`s and closes in a `finally`, so the ownership rule holds; the module-level `_CAPTURES` registry lets `stop`/`list`/`fetch` find a running capture across calls, and a process kill drops the socket so core stops the capture anyway (only the `/tmp` file survives). Both relaxations are scoped tightly: files live only under `Settings.PCAP_CAPTURE_DIR` (default `/tmp/wlanpi-mcp/captures`), `fetch_pcap_file` realpath-checks and refuses any path outside it, and it hands the file back as an MCP `EmbeddedResource` blob (`application/vnd.tcpdump.pcapng`) - so it is registered with `structured_output=False` and annotated `-> EmbeddedResource` only, and it reports errors by raising `ToolError` rather than returning `{"error": ...}` dicts. With structured output on, `MCPServer` serialises the blob into `structuredContent` as well as `content` and the pcap goes over the wire twice (issue #50); dropping the annotation is not enough, the flag is what turns it off. `tests/test_capture_file.py` pins this through `tool.run(args, Context(), convert_result=True)`: a `CallToolResult` with `structured_content is None` and exactly one `EmbeddedResource`. The blob's `uri` is a plain `str` and the field is `mime_type` in 2.x. Every byte still comes from the core capture WebSocket: same host, same JWT, no subprocess. The capture handle these tools take back is called **`capture_id`, not `session_id`** on purpose: `session_id` was the name the legacy MCP SSE transport reserved for its own routing query param (`POST /messages/?session_id=...`), and a tool argument sharing that name got dropped by some clients before it reached the server. Streamable HTTP carries its session in a header instead, but the handle keeps its name for existing callers - so `fetch_pcap_file`/`stop_pcap_file` expose `capture_id` (with `session_id` kept only as a back-compat alias) and every result carries `capture_id`. The filename embeds that id (`capture-<stamp>-<id>.pcapng`) so a capture is still resolvable from disk after the in-memory `_CAPTURES` registry is gone; the registry is a cache, the file is the record. The capture directory, the filename scheme and the path-confinement check live in `wlanpi_mcp/capture/storage.py`, shared by both tool families (the streaming tee and the file tools) so a file written by either is discoverable and fetchable by the same helpers - kept out of a tools module so neither imports the other. Reminder for tests: exercise these through `tool.run(args)` (the real dispatch+validation path), not only `.fn(...)` - the `session_id` collision was invisible to `.fn`-only tests.
### Authentication: JWT passthrough (deliberate design - do not add server-side auth)

This server implements **no authentication of its own**. The MCP client presents a JWT issued by wlanpi-core (`POST /api/v1/auth/token`) as `Authorization: Bearer <token>`, and that same token is passed through on every outbound wlanpi-core API call, where it is validated. This forces all MCP access through wlanpi-core's token system, even onbox.

The flow: `middleware/bearer_token.py` (daemon mode, always installed) rejects tokenless requests with 401 and stashes the Bearer token in the `auth/token_context.py` contextvar; `CoreClient._request` calls `get_token()`, which reads that contextvar. mcp 2.x removed `request_ctx` and runs each handler in the contextvars of the request that carried the call, so the contextvar is the only token source and concurrent requests with different tokens stay isolated (`tests/test_server.py` pins this with two overlapping requests). The middleware also sets a `current_request` contextvar (the Starlette `Request`), which `download_links.request_base_url()` reads for the Host header. It's pure ASGI middleware (not `BaseHTTPMiddleware`) on purpose so the downstream app runs in the same task.

The daemon transport is **stateless streamable HTTP on `/mcp`** (`streamable_http_path`, `stateless_http=True`, `json_response=True` in `create_http_app`). Every `POST /mcp` is a complete exchange with no server-side session, so a client that reconnects after a daemon restart or an idle gap cannot strand itself. That is why the legacy SSE transport was dropped: Claude Code re-opened a dropped stream without re-sending `initialize`, and the SDK then answered every tool call with `-32602 Invalid request parameters` (python-sdk issue #2579, closed as not planned). Do not reintroduce a session-holding transport without re-proving the per-token binding: the middleware still publishes a `sha256(token)` principal on `scope["user"]`, which the SDK's session manager would bind sessions to in stateful mode.

One scoped exception, for pcap downloads: `get_pcap_download_url` (in `tools/capture_file.py`) mints a random, single-use ticket that expires after `DOWNLOAD_TTL_S` (300 s) and returns a link to the `GET /pcap/<ticket>` custom route, so an agent can save a capture with plain `curl` instead of pulling base64 through its context with `fetch_pcap_file`. The ticket is not a credential for anything else: it names one file inside `PCAP_CAPTURE_DIR`, is popped on first use, and lives only in memory. It is minted only after the caller's JWT has been accepted by wlanpi-core (a `GET /api/v1/system/device/info` round trip), and `BearerTokenMiddleware` lets `/pcap/` and `/profiler-report/` (`get_profiler_reports`' links, same single-use rules) through without a Bearer token (`TICKET_PATH_PREFIXES`) because each route checks the ticket itself. Everything else still requires the JWT, and `/pcap/<ticket>`, `/profiler-report/<ticket>` and `/netconfig-secret/<ticket>` must stay the only routes under those prefixes (`tests/test_server.py` pins them). The third is the passphrase page `create_network_config` sends the user to through URL elicitation (`tools/netconfig_secrets.py`): its ticket is minted after the same core token check, is not spent by the browser (the page can be reloaded until the form is submitted once), and the stored passphrases are handed over once, only to a round carrying the JWT that minted it, then forgotten; unclaimed ones expire after `SECRET_TTL_S`. The page validates core's psk rules, sends no-store/no-referrer/CSP headers, and the passphrase never appears in any MCP message. The ticket does appear in the nginx and uvicorn access logs as part of the URL; that is accepted for a link that works once for five minutes. The `curl` command is built from the request's `Host` header, so the host is checked against a plain host[:port] pattern and both arguments are `shlex.quote`d. The token check and the sanitised base URL live in `wlanpi_mcp/download_links.py` so any other one-time link reuses them rather than copying them. Tests: `tests/test_capture_file.py` (minting) and `tests/test_server.py` (served once without a JWT, then 404; expired ticket refused; `/mcp` still 401).

Apart from those download tickets, the server never mints, verifies, refreshes, or caches tokens. A 401 from wlanpi-core (expired/revoked token) propagates back to the MCP client as a tool error - there is no retry, since the server doesn't own the token and can't refresh it. This applies mid-session too: if the token expires while a client is connected, tool calls start failing with 401 until the client reconnects with a fresh token. Stdio mode has no HTTP headers, so `WLANPI_CORE_TOKEN` in config/env is the fallback token source there.

The capture WebSocket uses the same token by the same rule, via the public `CoreClient.current_token()` wrapper - core requires it as the **first** message (`{"command":"auth","token":...}`) and closes with 4401 if it is missing, invalid, or put in the URL query string. Never place the token in the WebSocket URL.

Tests for this live in `tests/test_auth.py` (middleware: 401 on missing/non-Bearer token, contextvar propagation and reset, and the middleware's `current_request` reaching `request_base_url()`), `tests/test_server.py` (the assembled `/mcp` app end to end: forwarded LAN Host headers, a `tools/call` with no prior `initialize`, each request's own Bearer reaching wlanpi-core, two overlapping requests with different tokens held at a barrier, a 2026-07-28 "modern" request routed by headers, and core's status/detail or an unreachable core surfacing in the tool error) and `tests/test_client.py` (token forwarding, 401 passthrough without retry, missing-token error, stdio fallback).

### Tool conventions

Tools return error dicts (`{"error": "..."}`) rather than raising, so the LLM client gets a readable message. Elicitation and tasks are tested over the real `/mcp` dispatch with modern requests built by `tests/wire.py` (`test_elicit.py`, `test_tasks.py`); a tool that takes `ctx: Context` needs `ctx=Context()` when a test calls `.fn` directly (a blank Context is a client that cannot elicit). The exception is `fetch_pcap_file`, which raises `ToolError` so its result stays a bare blob (see above). The other exception is a failure talking to wlanpi-core: `CoreClient` raises `CoreAPIError` (an `httpx.HTTPStatusError` subclass) for a non-2xx, with core's `status_code` and `detail` intact - a string, an object like `{message, outcomes}`, or a plain-text body - and its message carries both, so the tool error the client sees says what core said. Don't swallow it into a generic message; tool docstrings should say what each core status means for the user. Every core-facing failure (`CoreAPIError`, `CoreUnavailableError` for a transport error or timeout, `CoreBadResponseError` for a 2xx with a non-JSON body, `MissingTokenError`) is a `ToolError` and a `ResourceError` that keeps its httpx/stdlib base, so existing handlers still match, because mcp 2.1+ otherwise reports any other exception as a bare "Error executing tool X" (or "Error reading resource <uri>", with a traceback at ERROR). `tests/test_server.py` asserts core's status and detail, and an unreachable core, survive the real `/mcp` dispatch for both `tools/call` and `resources/read`. Every `@mcp.tool` passes `annotations=hints.READ_ONLY | ADDITIVE | DESTRUCTIVE` (`wlanpi_mcp/tools/hints.py`); MCP treats an unannotated tool as destructive, and `tests/test_tool_annotations.py` pins each tool's class, so a new tool must be added there. Read-heavy resources in `resources/` use a small module-level TTL cache (`_cached_get`). Docstrings on tool functions are the MCP tool descriptions shown to the model - write them for an LLM consumer.

### Profiler reports

`get_profiler_reports` returns the profiler's per-client results: parsed JSON profiles inline (`output="json"`, the `pcapng` frame field stripped unless `include_frame`), a single-use link per file (`"links"`: each client's `.json`/`.txt`/`.pcap` plus the daily `reports/profiler-<date>.csv`, with one `curl --create-dirs` command for them all), or one link to a zip (`"zip"`). Newest client first, capped by `max_clients` (`0` = all), filterable by `mac` in any common format. Everything comes from wlanpi-core (2.4.8+, WLAN-Pi/wlanpi-core#378): `GET /api/v1/profiler/files` for the manifest (`?mac=` in dash form), then `GET /api/v1/profiler/files/{path}` (`CoreClient.get_bytes`) for each file, a few at a time; core confines the paths and refuses symlinks, and validates the JWT on each call, so there is no separate token pre-check. A 404 on the listing means core predates the endpoint and becomes an upgrade message; a 404 on one file (purged since the listing) is reported per profile for `json` and skipped for links/zip; any other core error propagates. Client MACs keep the profiler's dash form (core lists them with colons) and client directories that are not MACs are skipped. Its links reuse the pcap-ticket pattern but hold an in-memory snapshot of the bytes (capped at `MAX_DOWNLOAD_BYTES` per call), so a ticket never names a path, and they are served by `GET /profiler-report/<ticket>`. The sanitised `request_base_url` comes from `wlanpi_mcp/download_links.py`. Keep the tool's arguments and result shape stable: callers predate the move onto core (#58). Tests: `tests/test_profiler_reports.py`, plus the end-to-end link test in `tests/test_server.py`.

## Deployment

Ships as a Debian package (`debian/`) built with dh-virtualenv into `/opt/wlanpi-mcp`, depends on `wlanpi-core`, and runs as the `wlanpi` user via the systemd unit in `debian/wlanpi-mcp.service` (streamable HTTP transport, config from `/etc/wlanpi-mcp/config.env`, example in `install/etc/wlanpi-mcp/config.env.example`).
