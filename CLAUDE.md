# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An MCP (Model Context Protocol) server that exposes WLAN Pi capabilities - device info, service management, Wi-Fi scanning, packet capture, profiler, Bluetooth, VLANs - to AI assistants. It is a thin bridge to the `wlanpi-core` API on `https://localhost:31415`: every tool and resource goes through that API, and nothing runs local subprocesses or reads local files. Keep it that way - if a capability has no wlanpi-core endpoint, the endpoint gets added upstream first.

Almost all of that API is REST. The one exception is **packet capture**, which wlanpi-core exposes only as a WebSocket (`/api/v1/streaming/capture`) - so `wlanpi_mcp/capture/` speaks that protocol instead of HTTP. That is still core-API-only: same host, same JWT, still no local subprocess. The one deliberate exception to "no local file" is the file-backed capture family (`tools/capture_file.py`, see below), which persists the pcapng bytes it receives over that same WebSocket to a managed directory and reads them back - a scoped relaxation, not licence to read arbitrary device files or add other non-core transports.

`asyncio_mode = auto` is set in pyproject.toml, so async tests don't need `@pytest.mark.asyncio`. Lint and format tooling is configured via tox (`tox -e lint`, `tox -e formatcheck`, `tox -e format`) using flake8/black/isort/autoflake.

## Architecture

- `wlanpi_mcp/server.py` - `create_server()` builds the FastMCP instance and wires every module in. All tool/resource/prompt modules follow the same pattern: a top-level `register(mcp, client)` function containing `@mcp.tool()` / `@mcp.resource()` decorated closures. Adding a capability = new module in `tools/` or `resources/` + a `register()` call in `server.py`. The "Phase 1/2/3" comments reflect the order features were built, nothing more.
- `wlanpi_mcp/client/core_client.py` - `CoreClient`, the single async httpx client for wlanpi-core. Module-level singleton via `init_client()`/`get_client()`, created in `__main__.py` and passed to `register()` functions.
- `wlanpi_mcp/config.py` - pydantic-settings `Settings`, loaded from environment or `/etc/wlanpi-mcp/config.env`. Also holds `ALLOWED_SERVICES`, the allowlist that gates `start_service`/`stop_service`/`restart_service`. `ALLOW_POWER_CONTROL` (default true) gates `reboot_device`/`shutdown_device`. `TOOL_PROFILE` (`full`/`classroom`) and `TOOL_ALLOWLIST` pick the exposed tool set via `Settings.enabled_tools()`; `create_server(tools=...)` removes everything else after registration and fails on an unknown name. `CLASSROOM_TOOLS` is an allowlist on purpose, so a new tool stays out of classroom mode until it is added there. `WLANPI_CORE_TOKEN` is env-only: `settings_customise_sources` drops it from the config-file source.
- `wlanpi_mcp/client/tls.py` - `core_ssl_context()`, the one TLS trust decision for both the REST client and the capture WebSocket: `WLANPI_CORE_CA` is the trust anchor, verification is never disabled.
- `wlanpi_mcp/capture/` - the capture WebSocket client, used by `tools/capture.py`. `ws_client.py` derives the ws/wss URL from `WLANPI_CORE_URL` and drives the protocol (`CaptureSocket`: auth first, then `configure`/`start`/`subscribe`/`list_sessions`/`stop`; `CaptureError` carries core's error code so callers can branch on `INTERFACE_IN_USE`). `pcapng.py` and `dot11.py` are a stdlib-only incremental pcapng reader and radiotap/802.11 dissector **vendored from wlanpi-core `tools/capture_harness/capture_harness.py`** - keep them in sync with that reference rather than growing a parallel dissector, and do not pull in scapy/dpkt. The dissector has since been extended past the harness on purpose (the pcapng reader also yields a per-frame timestamp; `dot11.py` adds full radiotap decode, all frame type/subtype names, per-frame source/dest addresses, decoded management results, full RSN/WPA AKM/cipher/PMF detail, and the QBSS/BSS Load element) - these extensions are ours, so re-sync the *shared* parsing logic without dropping them. The streaming capture tools (`capture_scan`/`capture_observe`) return dissected summaries rather than raw pcap inline, but they now also tee the raw pcapng bytes to a file in the managed capture directory (via `CaptureSocket.consume`'s optional `raw_sink`) and return its `pcap_path`/`pcap_bytes`, so a summary can be verified against the frames with `fetch_pcap_file`; teeing is best-effort (`storage.try_open_capture_file`) so a storage problem never breaks a capture. Two views come out of the same frames - an AP table (`ScanTable.to_result()`, one row per BSSID with the compact security label plus full `akm`/`pairwise_ciphers`/`group_cipher`/`pmf`, and `stations`/`channel_utilization` from the QBSS Load element when present) and a per-frame log (`FrameLog`, exact per-kind counts always, plus up to `max_frames` records carrying addresses, radiotap and any decoded result). The per-frame record list is bounded by `max_frames` (0 = counts only, no records) so a busy capture can stay a summary rather than a text pcap — but the bound is caller-controlled, not a hard ceiling: a negative `max_frames` returns every frame, and there is no longer a `MAX_FRAMES_CAP`. For a genuinely complete capture prefer the file-capture tools over an unbounded `capture_scan`.

Capture ownership matters: a capture lives with its WebSocket, so closing the socket stops it. Owner flows must `stop()` and close in a `finally` - never leave an ownerless capture on the device - and every capture result states its `role` (`owner`/`subscriber`), `session_id` and running `config`. `capture_scan` auto-subscribes when the interface is already owned by another session. `CHANNEL_SET_FAILED` events are non-fatal and are surfaced in `channel_issues`: on single-radio devices, hops fail while the managed `wlan0` scans, and a partial capture must not be reported as complete.

File-backed capture (`wlanpi_mcp/tools/capture_file.py`: `start_pcap_file`/`stop_pcap_file`/`list_pcap_files`/`fetch_pcap_file`) is the one place that deliberately relaxes two of the invariants above - it returns *raw pcapng*, not a dissected summary, and it writes then reads a local file - to allow captures longer than the 60 s streaming window. `start_pcap_file` starts a capture, hands the owning `CaptureSocket` to a background asyncio task (`CaptureSocket.consume_raw`, which writes the pcapng byte stream verbatim instead of dissecting), and returns immediately with the on-device path and `session_id` while the capture keeps running past the tool call. That task still `stop()`s and closes in a `finally`, so the ownership rule holds; the module-level `_CAPTURES` registry lets `stop`/`list`/`fetch` find a running capture across calls, and a process kill drops the socket so core stops the capture anyway (only the `/tmp` file survives). Both relaxations are scoped tightly: files live only under `Settings.PCAP_CAPTURE_DIR` (default `/tmp/wlanpi-mcp/captures`), `fetch_pcap_file` realpath-checks and refuses any path outside it, and it hands the file back as an MCP `EmbeddedResource` blob (`application/vnd.tcpdump.pcapng`) - so its return is left un-annotated (a `-> dict` annotation would make FastMCP build a structured-output model and reject the blob). Every byte still comes from the core capture WebSocket: same host, same JWT, no subprocess. The capture handle these tools take back is called **`capture_id`, not `session_id`** on purpose: `session_id` was the name the legacy MCP SSE transport reserved for its own routing query param (`POST /messages/?session_id=...`), and a tool argument sharing that name got dropped by some clients before it reached the server. Streamable HTTP carries its session in a header instead, but the handle keeps its name for existing callers - so `fetch_pcap_file`/`stop_pcap_file` expose `capture_id` (with `session_id` kept only as a back-compat alias) and every result carries `capture_id`. The filename embeds that id (`capture-<stamp>-<id>.pcapng`) so a capture is still resolvable from disk after the in-memory `_CAPTURES` registry is gone; the registry is a cache, the file is the record. The capture directory, the filename scheme and the path-confinement check live in `wlanpi_mcp/capture/storage.py`, shared by both tool families (the streaming tee and the file tools) so a file written by either is discoverable and fetchable by the same helpers - kept out of a tools module so neither imports the other. Reminder for tests: exercise these through `tool.run(args)` (the real dispatch+validation path), not only `.fn(...)` - the `session_id` collision was invisible to `.fn`-only tests.
### Authentication: JWT passthrough (deliberate design - do not add server-side auth)

This server implements **no authentication of its own**. The MCP client presents a JWT issued by wlanpi-core (`POST /api/v1/auth/token`) as `Authorization: Bearer <token>`, and that same token is passed through on every outbound wlanpi-core API call, where it is validated. This forces all MCP access through wlanpi-core's token system, even onbox.

The flow: `middleware/bearer_token.py` (daemon mode, always installed) rejects tokenless requests with 401 and stashes the Bearer token in the `auth/token_context.py` contextvar; `CoreClient._request` calls `get_token()`, which reads the Bearer off the Starlette request the streamable HTTP transport binds to the MCP call (the SDK's `request_ctx`) and falls back to that contextvar. Tool calls run in a task the SDK's session manager spawns from inside the request, so the contextvar is inherited too, but the request header is the authoritative source. It's pure ASGI middleware (not `BaseHTTPMiddleware`) on purpose so the downstream app runs in the same task.

The daemon transport is **stateless streamable HTTP on `/mcp`** (`streamable_http_path`, `stateless_http=True`, `json_response=True` in `create_server`). Every `POST /mcp` is a complete exchange with no server-side session, so a client that reconnects after a daemon restart or an idle gap cannot strand itself. That is why the legacy SSE transport was dropped: Claude Code re-opened a dropped stream without re-sending `initialize`, and the SDK then answered every tool call with `-32602 Invalid request parameters` (python-sdk issue #2579, closed as not planned). Do not reintroduce a session-holding transport without re-proving the per-token binding: the middleware still publishes a `sha256(token)` principal on `scope["user"]`, which the SDK's session manager would bind sessions to in stateful mode.

The server never mints, verifies, refreshes, or caches tokens. A 401 from wlanpi-core (expired/revoked token) propagates back to the MCP client as a tool error - there is no retry, since the server doesn't own the token and can't refresh it. This applies mid-session too: if the token expires while a client is connected, tool calls start failing with 401 until the client reconnects with a fresh token. Stdio mode has no HTTP headers, so `WLANPI_CORE_TOKEN` from the environment (never the config file) is the fallback token source there. No `X-Wlanpi-Client` header is sent: core dispatches auth on the credential presented.

The capture WebSocket uses the same token by the same rule, via the public `CoreClient.current_token()` wrapper - core requires it as the **first** message (`{"command":"auth","token":...}`) and closes with 4401 if it is missing, invalid, or put in the URL query string. Never place the token in the WebSocket URL.

Tests for this live in `tests/test_auth.py` (middleware: 401 on missing/non-Bearer token, contextvar propagation and reset; `get_token()` request-context precedence), `tests/test_server.py` (the assembled `/mcp` app end to end: forwarded LAN Host headers, a `tools/call` with no prior `initialize`, and each request's own Bearer reaching wlanpi-core) and `tests/test_client.py` (token forwarding, 401 passthrough without retry, missing-token error, stdio fallback).

### Tool conventions

Tools return error dicts (`{"error": "..."}`) rather than raising, so the LLM client gets a readable message. Read-heavy resources in `resources/` use a small module-level TTL cache (`_cached_get`). Docstrings on tool functions are the MCP tool descriptions shown to the model - write them for an LLM consumer.

## Deployment

Ships as a Debian package (`debian/`) built with dh-virtualenv into `/opt/wlanpi-mcp`, depends on `wlanpi-core`, and runs as the `wlanpi` user via the systemd unit in `debian/wlanpi-mcp.service` (streamable HTTP transport, config from `/etc/wlanpi-mcp/config.env`, example in `install/etc/wlanpi-mcp/config.env.example`).
